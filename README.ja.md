# ari-harness

[English README](README.md)

`ari`(アリ)は、プログラミング作業を「頼んで、終わったら短い報告を受け取る」ための道具です。文章で書いた依頼(ブリーフ)を渡すと、GPT-6 のまとめ役(ルート)が作業を計画し、手分けして小さな作業係(サブエージェント)に同時に進めさせ、最後に「できた/途中/止まった」を 1 行目に書いた短い報告を返します。

人が直接話しかける道具ではありません。Claude Code のような「管理役の AI」が、下請けとして ari を呼び出す使い方を想定しています。

Agent Runtime Interface(ARI)という仕様(github.com/agent-runtime-interface/ari)とは関係ありません。

ari は個人の趣味の道具です。OpenAI とは関係がなく、OpenAI が認めたり支援したりしているものでもありません。

中身は `ari.mjs` と、囲いの決まりを書いた `sandbox.mjs`、小さな部品の `lib.mjs`(合わせて Node.js で約 1,500 行)で、[pi-coding-agent](https://github.com/earendil-works/pi) という部品の上に作られています。コマンド名は `ari`、リポジトリ名は `ari-harness` です。

## どんな人向けか

- ChatGPT Plus / Pro を契約していて、その Codex 用モデル(GPT-6 の Sol・Astra・Luna)に実装作業をさせたい人。
- すでに管理役の AI やスクリプトで作業を回していて、長いやりとりではなく、短くて機械で読める結果だけ返してくれる作業係がほしい人。
- Linux を使っていて、変更内容を自分(または管理役 AI)で確認できる人。
- 自分のコードに使う人。ari の囲いは、うっかりミスや AI がだまされて起こすミスを防ぐものです。信用できないリポジトリには、仮想マシンやコンテナーの中で使ってください(下の「囲い」参照)。

画面(UI)はありません。ari 自身は git のコミットやプッシュをしません。AI にも「頼まれない限りしない」よう指示していますが、AI は git コマンドを実行できるので、強制はできません。

## しくみ

1. 依頼文は、まとめ役(`/root`)に渡ります。まとめ役は、ファイルを読む・コマンドを実行する・ファイルを書き換える道具に加えて、作業係を呼ぶための道具(作業係を起動する、報告を待つ、追加の指示を出す、止める など)を使えます。
2. 作業係は、何も知らない状態から始まり、まとめ役が書いた短い指示(だいたい 1500 文字まで。長いと一度だけ差し戻されます)だけを見て動きます。作業係には「書き換えてよい範囲(スコープ)」が決められ、範囲がない作業係は読むだけの係になります。同時に動く作業係どうしの範囲は重なってはいけません。作業係がさらに作業係を呼ぶことはできません(`--depth` は 0 か 1)。
3. 作業係の報告は短く切られます(6 行・900 文字まで)。「変更したファイル」「確認コマンドの結果」などの事実は、AI ではなく ari 自身が書き足します。
4. まとめ役が終わったら、`--check` で指定した確認コマンド(たとえば `npm test`)を ari が実行します。失敗したら、その出力の最後の部分をまとめ役に一度だけ戻してやり直させます(出力の全文はファイルに保存し、その場所をまとめ役への連絡と最後の表示に書きます)。それでも失敗し、まとめ役が「できた(DONE)」と報告していたら、結果は `PARTIAL`(途中まで)になります。`BLOCKED`・`FAILED` の報告はそのままです。
5. 最後に、まとめ役の報告(12 行・1800 文字まで。全文は別ファイルに保存)と、ari が計算した情報(下の「出力」参照)を表示します。

ほかにも次のような決まりが組み込まれています。

- **使いすぎ防止:** 道具を使える回数はまとめ役 250 回、作業係 60 回まで。作業係の 1 件ごとに、動き始めてから 30 分の期限があります。期限の時点で動いている AI とのやりとりは止め、期限のあとは AI とのやりとりを始めません(確認コマンドが失敗したあとのやり直しも含みます)。期限の時点で動いている確認コマンドは止めないので(こちらには別に 10 分の制限があります)、その分だけ遅れて終わることがあります。コマンドの出力は 12,000 文字に縮めて AI に見せます。
- **寄り道防止:** 編集のあとに確認コマンドばかり 4 回続くと「もう確認はいいので報告して」と伝えます。頼まれていないのに新しい説明書ファイル(.md など)を作ろうとすると、一度止めます。
- **固まり対策:** AI からの返事が長く止まったら、接続を切ってつなぎ直します(1 人あたり 3 回まで)。
- **プロジェクトの決まりごと:** 作業フォルダーとその上のフォルダーにある `AGENTS.md` / `CLAUDE.md` を、まとめ役だけが読みます(`--no-context` で読ませないこともできます)。ari 専用の `~/.local/state/ari/pi/AGENTS.md` を作れば、全体向けの決まりごととして読みます。秘密のファイル(やそこへのリンク)は読みません。pi 自体の設定(`.pi/settings.json` のパッケージ、拡張機能、`APPEND_SYSTEM.md` など)は一切使いません。
- **優先レーン:** 標準では OpenAI に「優先処理(priority)」を頼みます。`--no-fast` で止められます。
- **変更の記録:** git のフォルダーでは、開始時点の状態をこっそり記録します(作業中のファイルには触りません)。そのおかげで「この実行で変わったファイル」を出せます(git が管理しているファイルは名前に関係なくすべて正確に(日本語などの名前もそのまま扱います)、管理外のファイルは新しくできたものと、大きさ・更新時刻が変わったもの。管理外の `node_modules/`・`__pycache__/`・`*.pyc` などのキャッシュは省きます)。

## 必要なもの

- Linux と Node.js 22.19 以上(pi-coding-agent 0.87.0 の条件)、`bash`。
- `bwrap`(bubblewrap)。標準の「囲い(サンドボックス)」に使います。ari は起動時に動くか確かめ、動かなければ始めずに止まります(`--sandbox off` のときを除く)。
- `git`(なくても動きますが、変更ファイルの一覧が不完全になります)、`rg`(ripgrep。あると良い)。
- pi-coding-agent が対応している ChatGPT / Codex のログイン(下記)。

## インストール

```sh
git clone https://github.com/aiueo52/ari-harness.git
cd ari-harness
npm ci
ln -s "$PWD/ari.mjs" ~/.local/bin/ari   # PATH の通ったフォルダーならどこでも
ari --help
```

## ログイン(事前準備)

ari 自身にはログイン機能はありません。pi-coding-agent の「ChatGPT Plus/Pro (Codex)」でログインしたときに pi が保存する情報(`~/.pi/agent/auth.json` の `openai-codex` の部分)をそのまま使います。

`npm ci` で pi のコマンドも入るので、一度だけ次のようにログインします。

```sh
npx pi        # 起動したら /login と打ち、ChatGPT Plus/Pro (Codex) を選ぶ
```

くわしくは pi の[説明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/providers.md)を見てください。このログイン情報のファイルは、絶対に公開したり貼り付けたりしないでください。

**利用規約について:** ari は OpenAI とは関係がなく、OpenAI に認められたものでもありません。自分の契約の規約が、このような外部の道具からの利用や、自動でたくさん同時に動かす使い方を認めているかは、使う前に各自で確認してください。また ari は、使用量を公開されていない ChatGPT の窓口から読んでいます(「料金と使用量」参照)。

## 使い方

主なオプション(`ari --help` でも見られます。`--help` に出ないものは表の下に書いています):

| オプション | 意味 |
|---|---|
| `-C フォルダー` | 作業するフォルダー(省略時は今いるフォルダー) |
| `-m モデル` | まとめ役のモデル。`sol`(標準)、`astra`、`luna` |
| `-e 強さ` | まとめ役の考える強さ。`low`〜`max` |
| `--child モデル` | 作業係の標準モデル(標準は `luna`) |
| `--child-effort 強さ` | 作業係全員の考える強さを固定する |
| `--max 数` | 同時に動く作業係の数(標準 12) |
| `--depth 数` | 0 = 作業係を使わない、1 = まとめ役が作業係を呼ぶ(標準。作業係はさらに呼べません) |
| `--check "コマンド"` | 最後に実行する確認コマンド。失敗したら一度だけやり直し |
| `--sandbox off` | 囲いを外す(おすすめしません。使うと警告が出ます) |
| `--allow-secret 場所` | 隠している秘密ファイルを、この実行のコマンドにだけ読めるようにする(何度でも指定可。下記参照) |
| `--no-fast` | 優先レーンを使わない |
| `--resume 実行ID "追加の指示"` | 終わった実行の続きを頼む |
| `--status` | 週の使用量と最近の実行を表示 |
| `--sandbox-check` | 実行と同じように囲いを用意して、使えるかどうかを表示して終わる(依頼文も AI も使いません) |
| `--json` | 結果を JSON で出す |
| `-q` | 途中経過を表示しない |

`--help` に載っていないものとして、`--force`(週の使用量が 99% 以上でも実行する)と `--no-context`(`AGENTS.md` などを読ませない)があります。

### 例

依頼文を標準入力で渡す(いちばん普通の使い方):

```sh
ari -C ~/src/myapp - <<'EOF'
myapp export に --dry-run オプションを追加してください(src/cli/export.ts)。
付けたときは、書き出す予定のファイル名を表示するだけで、何も書き込まないこと。
新しいライブラリは追加しないこと。
完成の条件: npm test が通り、myapp export --dry-run で何も書き込まれないこと。
EOF
```

確認コマンド付き、作業係を強いモデルに:

```sh
ari -C ~/src/myapp --check "npm test" --child sol - < brief.txt
```

前回の続き(実行 ID は出力の最後に出ます):

```sh
ari --resume 202609280130-1a2b "空のフォルダーは一覧に出さないようにしてください。"
```

## 出力

まとめ役の報告のあとに、ari が書いた `[ari]` で始まる行が続きます(数字は例です)。

```text
DONE: myapp export に --dry-run を追加しました。npm test は通っています。
src/cli/export.ts: オプションを追加し、指定時は書き込みを省略。
確認: npm test(42 件成功)

[ari] run 202609280130-1a2b · 312s · 3 sub-agents (luna 2, sol 1) · tokens 820k in (610k cached) / 41k out
[ari] changed (2): src/cli/export.ts, test/export.test.ts
[ari] check PASS: npm test
[ari] codex weekly: 41% → 43% used, resets 10/2 09:00
[ari] log: /home/you/.local/state/ari/runs/202609280130-1a2b · snapshot 1a2b3c4d5e6f
```

- 1 行目の最初の言葉が結果です。`DONE`(完了)、`PARTIAL`(途中まで)、`BLOCKED`(人の判断が必要で止まった)、`FAILED`(失敗)。
- 最後の確認コマンドが失敗し、まとめ役の報告が `DONE` だったときは、報告の上に `PARTIAL: the acceptance check failed (コマンド); the root's report follows.` という行が付きます。確認に失敗した実行が `DONE` になることはありません。`BLOCKED`・`FAILED`・`PARTIAL` の報告はそのままです。
- 実行中に git の設定をすり替えられるファイル(`.git/commondir` など)が作られたり、変えられたり、消されたりしたら、`WARNING` の行が出ます。
- `--json` の結果には、最後の `WARNING` 行と同じ内容が `warnings` として入ります。
- 終了コード: 0 = DONE、2 = PARTIAL(確認コマンドに失敗した DONE を含む)、3 = BLOCKED、1 = FAILED やオプションの間違いなど、130 = 中断。
- 記録は `~/.local/state/ari/runs/実行ID/` に残ります。AI が読んだファイルの中身もそのまま含まれるので、人に渡すときは注意してください。長いコマンド出力の全文と、失敗した確認コマンドの出力の全文(`*.check.txt`)は `runs/実行ID/tmp/` に入ります。ari はこのフォルダーを自分だけが読める設定(0700 / 0600)にし、囲いの中からは見えないようにしています(その実行の `tmp/` だけは読むだけ可。後の実行が前の記録を読めないように)。

## 管理役 AI からの使い方

1. 短くて、それだけで分かる依頼文を書く(目的、決まっていること、ファイルの場所、完成の条件)。確認できるコマンドがあれば `--check` に入れる。
2. `ari -C リポジトリ -` に依頼文を渡し、終わるまで待つ(数分〜数十分かかります)。
3. 終了コードか 1 行目で結果を判断し、`[ari]` の行を読む。途中経過を全部読む必要はありません。
4. 変更は自分で確認する(`git diff スナップショットID` と `git status`)。ari 自身はコミットしませんが、依頼文で頼めば AI がコミットすることはあるので、`git log` も見てください。
5. 途中までなら `--resume` で続きを頼む。
6. 週の使用量が残り少ないと表示されたら、人に知らせる。

## 囲い(サンドボックス)でできること・できないこと

**最初に読んでください。** この囲いは、うっかりミスや、AI がだまされて起こすミスを防ぐための「できる範囲の柵」です。**本気で攻撃してくる相手から守る金庫ではありません。** 公開前の審査では、回を重ねるたびに新しいすり抜け方が見つかりました。見つかったものは直しましたが、同じ種類のすり抜け方がまだある可能性は高いです。信用できないリポジトリや依頼文を扱うときや、放っておいて動かすときは、必要なファイルとログイン情報だけを入れた仮想マシンやコンテナーの中で使ってください。

標準の `--sandbox workspace` で **ari が約束するのは、次の一覧がすべてです**。どの項目も `test/sandbox.test.mjs` の試験で確かめています。**ここに書いていないものは守られません。** 分かっている穴は次の節に書いてあります。

**コマンド**(AI が実行する `bash`、`--check`、ari 自身が使う git)は `bwrap` の中で動きます。

1. **書き込める場所**は、作業フォルダー、`/tmp`(パソコン本体と共有)、コマンドごとの専用の `/dev/shm`、`~/.cache`、`~/.npm`、cargo の `~/.cargo/registry`・`~/.cargo/git`・ロック用ファイル、`ARI_EXTRA_WRITABLE` で足した場所だけです。ほかはすべて読むだけです(`~/.bashrc`、`~/.cargo/bin`、cargo の設定も)。
2. **危ない書き込み先は起動時に拒否します。** 作業フォルダーや書き込める場所が、ホームフォルダーそのものかそれを含む場所、秘密の場所や接続口の中、あとで囲いの外で実行される場所(`sandbox.mjs` の `ESCAPE_PATHS`。シェルの起動ファイル、`~/.local/bin`、自動起動、systemd、git の設定、`~/.cargo` など)と重なる場所、`/proc`・`/dev`・`/sys`・`/run` と重なる場所の場合です。場所はリンク先まで確かめ、たどりきれないものは拒否します。
3. **秘密の場所は隠します**(一覧は `sandbox.mjs` の `SECRET_DEFAULTS` と `ARI_EXTRA_SECRETS`)。ari 自身の過去の記録も隠します(今の実行の一時フォルダーだけは読むだけで見えます)。一覧はコマンドごとに確かめ直すので、実行中にできた秘密も、その後のコマンドからは隠れます。秘密がリンクなら、リンク先ごと隠します。書き込める場所から秘密までの途中のフォルダーは、名前を変えられません。
4. **ログイン中の接続口も隠します。** 実行時フォルダー(`$XDG_RUNTIME_DIR`)は空に見え、`SSH_AUTH_SOCK`・`DBUS_SESSION_BUS_ADDRESS`・`GPG_AGENT_INFO` は消します。
5. **プロセス:** コマンドからは自分のプロセスしか見えません。
6. **シェルの設定ファイル:** ari が起動する bash はすべて `--norc --noprofile` で動きます(囲いの中のものと、pi の bash 道具のために `bwrap` を起動するパソコン本体側のもの)。
7. **git**: 作業フォルダーの git フォルダー、そのサブモジュールの git フォルダー(`.git/modules/` の下。何段深くても)、起動時に作業フォルダーの中にあった、自分の `.git` フォルダーを持つ別のリポジトリ、書き込める場所にある作業フォルダーの外の git フォルダー(linked worktree のもの、サブフォルダーで ari を動かしたときのリポジトリのもの)について:
   - `config`・`hooks`、すでにある `commondir`・`config.worktree`・worktree の `gitdir` は書き込めません。git フォルダーの場所を書いた `.git` ファイル(linked worktree やサブモジュールのもの)も同じです。
   - これらの git フォルダー、その途中のフォルダー、サブモジュールの作業フォルダーへ至るフォルダーは、名前を変えられません。
   - 実行中に `commondir`・`config.worktree`・`gitdir`・`.git` ファイルが作られたり、変わったり、消されたりしたら、最後の表示と `--json` の `warnings` で知らせます。
   - ari 自身の git は囲いの中で動くので、リポジトリの設定が指すフィルターが囲いの外で動くことはありません。コミットなど普通の git 操作はできます。
   - linked worktree(`git worktree add` で作ったもの)や、リポジトリのサブフォルダーも作業フォルダーとして使えます。囲いを用意する前にリポジトリの git フォルダーを知るため、ari は起動時に、AI が動き出す前に一度だけ、パソコン本体で `git rev-parse` を実行します(fsmonitor とフックは止め、書き込める場所にある `git` は使いません)。それ以外の ari 自身の git はすべて囲いの中で動きます。`ari --sandbox-check -C フォルダー` で、依頼文なしにこの起動処理だけを行い、そのフォルダーで囲いが使えるかを確かめられます。
   - 「書き込めない」の例外が 1 つあります。ari 自身の git(開始時の記録)は、作業フォルダーの外の git フォルダー(サブフォルダーや linked worktree で ari を動かしたときのリポジトリのもの)に書き込むことがあります。その場合も config・hooks・行き先ファイルは書き込めません。AI のコマンドは、それが書き込める場所にない限り、そこに書き込めません。
8. **込み入った配置は、守る代わりに拒否します**(起動しない、またはそのコマンドを拒否)。上の git の場所やそこへ至る途中のどこかにシンボリックリンクがある。`.git` ファイル・`commondir` が指す道筋に、書き込める場所にあるシンボリックリンクがある(リンクの先の道筋も順にたどって確かめます)。git フォルダーに config が無い(次の確認を通る `commondir` があれば別)。`commondir` が、git の決まった配置どおりの git フォルダー(linked worktree のものなら、その `worktrees/` を持つ git フォルダー、それ以外なら自分自身)を指していない、または指す先に config が無い。読むだけの場所にある git フォルダーの config・hooks・行き先ファイルが、書き込める場所へつながっている。`.git` ファイルや `commondir` が、上のどれでもない git フォルダーを指している(場所に関係なく。道筋は OS と git と同じように解釈します。たとえば `link/..` は、リンク先の一つ上のフォルダーです)。git がリポジトリや設定を探す場所を変える環境変数が設定されている(`GIT_DIR`・`GIT_WORK_TREE`・`GIT_COMMON_DIR`・`GIT_INDEX_FILE`・`GIT_OBJECT_DIRECTORY`・`GIT_ALTERNATE_OBJECT_DIRECTORIES`・`GIT_CEILING_DIRECTORIES`・`GIT_DISCOVERY_ACROSS_FILESYSTEM`・`GIT_CONFIG_GLOBAL`・`GIT_CONFIG_SYSTEM`・`GIT_CONFIG_COUNT`・`GIT_CONFIG_KEY_*`/`VALUE_*`・`GIT_CONFIG_PARAMETERS`、または相対パスの `XDG_CONFIG_HOME`)。git の設定に include(`include.path`・`includeIf.*.path`)が一つでもある(リポジトリ・サブモジュール・worktree の config と config.worktree、`~/.gitconfig`、XDG の git 設定)。include のある設定には対応していないので、ari はその先を読まずに拒否します。サブモジュールの `core.worktree` が、ari が git と同じように解釈できない書き方(`~ユーザー名/`・`%(prefix)/`・`:(...)`)を使っている。全体の git 設定そのものが書き込める場所にある。

実際の影響: コマンドの中で裏で起動したものは、そのコマンドが終わると止まります(サーバーは、起動と利用を 1 つのコマンドの中で行ってください)。接続口が必要なコマンド(GPG でのコミット署名、デスクトップアプリとのやり取り)は失敗します。長いコマンド出力の全文は、今の実行専用の一時フォルダーに保存されます。

**ファイルを読む・書く道具**(`read`・`edit`・`write`)は ari 本体の中で動くので、ari が場所を確かめます。書かれたままの形とリンクをたどった先の両方で確かめます。道具に渡された場所は、まず pi と同じように文字の上で整えます(`hop/../x` は、`hop` が何であっても `x` になり、pi もそこを開きます)。そのあと、その場所にあるリンクを OS と同じようにたどります(リンク先の中の `link/..` は、リンク先の一つ上のフォルダーです)。そのようにたどりきれない場所(リンクのループ、41 個以上のリンク、行き先の無いリンク、実在する部分より後ろの `.`・`..`)は、3 つの道具すべてで拒否します。

9. `edit`・`write` は上の書き込める場所だけに書けます。秘密の場所(まだ無いものも含む)と、上の git のファイルには書けません。
10. `read` は、秘密の場所(`--allow-secret` で許したものも)、接続口、`/proc`・`/dev`、過去の実行の記録を読めません。pi の読む道具が代わりに探す似た名前も確かめます。`AGENTS.md`・`CLAUDE.md` のような自動で読み込むファイルも、読む前に同じように確かめます。

### プログラムに秘密ファイルを 1 つだけ読ませる: `--allow-secret`

API キーのファイル(たとえば `~/.config/openrouter/api_key`)を読むアプリを動かす作業では、次のようにします。

```sh
ari --allow-secret ~/.config/openrouter/api_key -C ~/src/myapp - < brief.txt
# または: ARI_ALLOW_SECRETS=~/.config/openrouter/api_key ari ...
```

その実行の間だけ、その場所が**コマンドから**、**読むだけ**できるようになります(`~/.cache` のような書き込める場所の中にあっても、書き込みはできません)。何度でも指定でき、開始時の記録に出ます。許可できるのは、上の一覧で隠している秘密そのものか、その中の場所だけです。それ以外や、作業フォルダーや書き込める場所を含むような大きな指定は拒否されます。AI がファイルを読む道具では、引き続き読めません。ただし、AI が実行するコマンドでファイルの中身を表示させることはできてしまい、コマンドの出力は AI に届きます。信用できる作業のときだけ、なるべくファイル 1 つだけを許可してください。

### 守れないもの

上の一覧にないものすべてです。特に次のものは守れません。

- インターネットには自由につながります。
- 環境変数(API キーなどを入れている場合)はそのまま見えます(上の接続口用のものを除く)。
- 秘密の一覧にない場所は読めます(ほかのアプリの設定、プロジェクトの `.env` ファイルなど)。
- `/tmp` はパソコン本体と共有です。`/dev` も共有なので(`/dev/shm` だけ専用)、あなたが使える機器はコマンドからも使えます。画面(X11)にもつながるので、コマンドが画面にウィンドウを出したり、X11 の仕組み上ほかのウィンドウの入力を読んだり送ったりできてしまいます。
- `~/.cache` や `~/.npm` のキャッシュに細工されると、あとで囲いの外で使う道具(pip・uv・Go・npx など)に影響するおそれがあります。
- 作業フォルダーの中で AI が書いたもの(スクリプト、`package.json`、Makefile、`.envrc`、`core.hooksPath` やリンクを通して git が使うフックのスクリプト(`.husky/` など)、fsmonitor やフィルターが指すスクリプトなど)は、あとであなたが実行したり、そのリポジトリで git を使ったりすると、あなたの権限で動きます。実行する前に変更内容を確認し、最後の警告は必ず確かめてください。
- 上の一覧を超える git: まだ無い `commondir`・`config.worktree` は作れてしまいます(知らせるだけです)。書き込める場所にあるほかのリポジトリ(`/tmp` や `~/.cache` にある、この実行のものではない clone、実行中に作業フォルダーの中に現れたリポジトリ、`git init`・`git clone` で作られたもの)は守りません。
- 場所を確かめてから pi が実際に開くまでの間に、同時に動いている別のコマンドがファイルやリンクをすり替えることは防げません。
- **実行後のあなたのシェル:** ふだん開くシェルは、パソコン本体で `~/.bashrc` や `~/.profile` を読みます。これらが書き込める場所にあるファイルを読み込んでいると(作業フォルダー、`~/.cache`、`~/.npm`、仮想環境の `activate`、プロジェクトの `.envrc` など)、AI がそこにコードを仕込め、次にシェルを開いたときにあなたの権限で動きます。設定ファイルがそうした場所を読み込まないようにしてください。これとは別に、あなたが設定した `BASH_ENV` は囲いの中で読まれます。それが書き込める場所にあるなら、ari を起動する前に消してください。
- 「読むだけの係」やスコープの制限は、ファイル編集の道具にだけ効きます。コマンド経由の書き込みは止めません。
- `--sandbox off` にすると全部なくなります(起動時に警告が出ます)。そのとき ari 自身の git は、フックと fsmonitor だけは止めますが、フィルターは動きます。
- リポジトリの中の文章などに AI をだます指示が紛れ込む危険(プロンプトインジェクション)は、ほかの AI 道具と同じくあります。

## 料金と使用量

- API の従量料金ではなく、ChatGPT / Codex の契約の「使用量の枠」を使います。作業係が同時にたくさん動くほど、早く減ります。`--max` で数を、`--child` / `--child-effort` で安いモデルや強さを選べます。
- 週の使用量は、ChatGPT の非公開の窓口(`chatgpt.com/backend-api/wham/usage`)から、ログイン情報を使って読んでいます。変わる可能性があり、読めないときは `unknown` と出ます。これが契約の規約に合うかどうかも、各自で確認してください。
- 週の使用量が 99% 以上だと、ari は始めずに止まります(`--force` で無理に実行可能)。新しい作業係も起動しません。
- 標準で優先レーンを頼みます。これが使用量にどう数えられるかは OpenAI 次第なので、気になる場合は `--no-fast` を使ってください。

## 分かっている制限

- 標準では Linux 専用です(bubblewrap を使うため)。
- GPT-6 の Codex モデルと pi の `openai-codex` 接続が前提です。
- pi-coding-agent 0.87.0 に合わせて作っているので、ほかの版では動かない可能性があります。
- `--resume` は元の作業フォルダーで続けます(`-C` は無視されます)。
- git 以外のフォルダーでは、変更ファイルの一覧が不完全になります。
- 自動テスト(`npm test`。AI は呼びません)は、囲い・設定の読み込み・結果の判定などの部分だけです。
- ari は `TMPDIR` を実行専用のフォルダーにします。囲いありのときコマンドには元の `TMPDIR` を戻しますが、`--sandbox off` のときはそのフォルダーがそのまま使われます。`tools/` の 2 つのスクリプトは調整用の実験で、実行すると実際に使用量を消費します。
